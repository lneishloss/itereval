# The Hidden Lever in AI Coding Costs: Why Output Tokens Matter More Than Input

The AI coding assistant market hit $7.4 billion in 2025 and is projected to reach $30 billion by 2032 [1]. GitHub Copilot alone has 20 million users and generates 46% of all code written by developers [2]. Behind every autocomplete suggestion and every Claude Code session, there's an API call — and most of those API calls are priced asymmetrically: output tokens cost 3-5x more than input tokens.

I ran controlled experiments on 164 HumanEval problems and found that a simple system prompt change — telling Claude to write compact code — reduces output tokens by **34%** and cost-per-solve by **18.3%**, with no meaningful accuracy loss (paired permutation test, p = 0.0003). Separately, minifying input prompts (preserving docstrings) and generated code in error feedback reduces cost-per-solve by **12.9%** with no significant accuracy degradation. These are small interventions with measurable impact. At the scale this industry operates, "small" adds up.

## Why This Matters Beyond API Bills

The International Energy Agency projects data center electricity consumption will exceed 1,000 TWh by 2026, with AI-driven compute growing at 30% annually [3]. Inference — not training — accounts for over 90% of operational energy consumption for LLM services [4]. Every output token generated by a coding agent consumes compute, electricity, and water for cooling.

Recent research benchmarking the energy footprint of LLM inference found that a 0.42 Wh query, scaled to 700 million queries per day, aggregates to annual electricity consumption comparable to 35,000 U.S. homes [5]. Output length is one of the strongest predictors of per-query energy cost. A 35% reduction in output tokens translates directly to reduced computation — fewer forward passes through the model, less memory bandwidth, less cooling.

This isn't about individual developers saving a few dollars. It's about whether the infrastructure scaling up to serve millions of AI coding sessions per day is doing so efficiently. The answer, based on my measurements, is: not yet.

## Pass@k Doesn't Model Reality

The standard benchmark for LLM coding ability is pass@k [6]: give the model a problem, generate k independent attempts, check if any pass. This is the metric from OpenAI's Codex paper, and it remains the default in most coding evaluations.

But this doesn't reflect how anyone actually uses AI for coding. When Claude Code writes buggy code, it doesn't throw away the attempt and start over. It runs the code, reads the error, and tries to fix it. Before agentic tools existed, the universal debugging workflow was: copy the error, paste it back, say "fix this."

Pass@k treats each attempt as independent. Real-world usage is iterative — each attempt builds on the failure of the last. This distinction matters because it changes both the success rate and the cost profile.

## The Iterative Evaluation Framework

Standard pass@k on HumanEval:

1. Feed a prompt and function signature to the LLM
2. LLM generates code
3. Test harness runs the code — pass or fail
4. Repeat k times independently

The iterative framework changes step 4:

1. Feed a prompt and function signature to the LLM
2. LLM generates code
3. Test harness runs the code — pass or fail
4. **If failed, reconstruct the prompt from the original problem plus the most recent failed code and error output.** Repeat from step 2, up to k attempts. Only the last failure is retained — earlier attempts are not accumulated in the context.

> **NOTE:** This is a "last-error-only" feedback strategy: each retry sees `original_prompt + most_recent_error`, not the full history of all previous attempts. This keeps context size bounded and is a deliberate design choice. Accumulating all errors would provide richer context but at higher token cost — a potential future IV to test.

This is a small change to the evaluation protocol, but it dramatically improves ecological validity. It also creates a richer cost signal: each retry adds tokens, and we can measure exactly how many.

## Cost-Per-Solve

With iterative attempts, we can define a metric that captures what matters in practice: **cost-per-solve (CPS)** — the total API cost divided by the number of problems successfully solved.

$$CPS = \frac{\sum \text{Input Cost} + \sum \text{Output Cost}}{\text{Problems Solved}}$$

This single number is accuracy-adjusted by construction. A strategy that solves fewer problems has a higher CPS (denominator penalty). A strategy that takes more retries accumulates cost (numerator penalty). CPS lets you directly compare prompting strategies, input transformations, and models on the axis that matters: *how much does it cost to get a correct answer?*

Kapoor et al. [7] demonstrated that agent evaluations without cost controls are scientifically meaningless — they found agents with similar accuracy levels varying by 50x in cost. But they didn't formalize a per-problem cost metric for iterative settings. The Aider benchmark tracks cost per task but caps retries at two attempts without computing CPS as a first-class metric. The iterative CPS framework fills this gap.

## Experiment Design

I tested two interventions on the full 164-problem HumanEval benchmark using Claude Sonnet (`claude-sonnet-4-20250514`), temperature=0, with up to 3 iterative attempts per problem. Both experiments share a single control arm for statistical efficiency.

**Experiment 1: Prompt engineering (conciseness instruction)**

Both arms receive the same user prompt (the original HumanEval problem). The treatment arm's system prompt instructs Claude to write compact, minified-style code with short variable names and collapsed logic. The control arm's system prompt asks for clean, correct code with no style constraints.

**Experiment 2: Python minification**

Both arms use the identical control system prompt. The treatment arm applies two transformations:

1. **Prompt minification** (`minify_prompt`): The input prompt is minified — blank lines removed, comments stripped, internal whitespace collapsed — while preserving docstrings verbatim, since the docstring contains the problem specification (description, examples, constraints).
2. **Code minification in error feedback** (`minify_python`): When a failed attempt's code is embedded in the error feedback for the next retry, it is first minified (comments removed, whitespace collapsed, redundant syntax eliminated). This reduces token growth across retries.

Both transforms are applied on every iteration — the growing prompt (original + error feedback) is re-minified before each API call.

### Statistical Methods

Following Miller [8] on the importance of confidence intervals and paired analysis in LLM evaluation, Bowyer et al. [9] on CI method selection for small-sample binary outcomes, Dietterich [10] on paired classifier comparison, and Dror et al. [13] on significance test selection for NLP:

- **Wilson score intervals** for solve rates — preferred over normal approximation (Wald) intervals for binary outcomes with N < 300 [9]. (Miller [8] recommends CLT-based Bernoulli standard errors, which work well at large N but can produce invalid intervals for the sample sizes typical of coding benchmarks; Bowyer et al. [9] demonstrate that Wilson intervals provide reliable coverage at small N.)
- **McNemar's test** for paired binary outcomes — the correct test for comparing two conditions on the same problems [10], using exact binomial test when discordant pair counts are below 25. Dror et al. [13] also recommend McNemar's for paired binary evaluations.
- **Bootstrap confidence intervals** (1,000 resamples) on cost-per-solve savings — non-parametric, with no distributional assumptions. Bootstrap iterations where an arm has zero solves are dropped (CPS is undefined); the dropped fraction is reported so the CI's reliability can be assessed.
- **Paired permutation test** on per-problem total costs — assumption-free significance test for right-skewed cost distributions where a paired t-test's normality assumption would be violated. Note: this tests whether per-problem costs differ between arms, which is related to but distinct from the CPS savings metric (which also incorporates solve-rate differences).

## Results

### Experiment 1: Prompt Engineering

| Metric | Control | Treatment | Delta |
|---|---|---|---|
| Solve rate (3 attempts) | 97.6% (CI: 93.9–99.0%) | 97.6% (CI: 93.9–99.0%) | 0pp |
| Cost per solve | $0.00263 | $0.00215 | **-18.3%** |
| Output tokens | 20,244 | 13,359 | **-34.0%** |
| Input tokens | 39,198 | 47,936 | +22.3% |
| Total cost | $0.4213 | $0.3442 | -18.3% |
| Paired permutation p-value | | | **0.0003** |
| Bootstrap 95% CI on CPS savings | | | **[8.9%, 27.2%]** |

The treatment uses *more* input tokens (the conciseness instruction is longer, and slightly more retries accumulate error feedback). But it saves 34.0% on output tokens. Since output tokens cost 5x more than input ($15/M vs $3/M on Sonnet), the output reduction dominates. The net result: 18.3% cost-per-solve savings, with the bootstrap 95% CI excluding zero and a paired permutation test confirming significance (p = 0.0003).

### Experiment 2: Python Minification

| Metric | Control | Treatment | Delta |
|---|---|---|---|
| Solve rate (3 attempts) | 97.6% (CI: 93.9–99.0%) | 98.2% (CI: 94.8–99.4%) | +0.6pp |
| Cost per solve | $0.00263 | $0.00229 | **-12.9%** |
| Output tokens | 20,244 | 17,451 | **-13.8%** |
| Input tokens | 39,198 | 35,878 | -8.5% |
| Total cost | $0.4213 | $0.3694 | -12.3% |
| Paired permutation p-value | | | **0.001** |
| Bootstrap 95% CI on CPS savings | | | **[3.9%, 21.9%]** |

Minification removes comments, blank lines, and redundant whitespace from both the input prompt and the generated code in error feedback — while preserving docstrings that contain the problem specification. This is a lossy transformation (comments are discarded), but it does not degrade accuracy (and is directionally *higher* in the treatment arm, though the difference is not significant). CPS savings are 12.9%, and total cost savings reach 12.3%. The two interventions (prompt engineering and minification) use orthogonal mechanisms and are composable.

## The Output Token Insight

The key finding is not just that prompt engineering saves money. It's *where* the savings come from. Look at the token breakdown for Experiment 1:

- Input tokens **increased** by 22.3%
- Output tokens **decreased** by 34.0%
- Net cost **decreased** by 18.3%

This only makes sense when you account for asymmetric pricing:

| Model | Input $/M | Output $/M | Ratio |
|---|---|---|---|
| Claude Haiku 3.5 | $1.00 | $5.00 | 5x |
| Claude Sonnet 4 | $3.00 | $15.00 | 5x |
| Claude Opus 4 | $15.00 | $75.00 | 5x |
| GPT-4o | $2.50 | $10.00 | 4x |
| GPT-4 Turbo | $10.00 | $30.00 | 3x |

A 34% reduction in output tokens at 5x the price saves more than a 22% increase in input tokens costs. The output side is the dominant lever across every major API provider.

Microsoft's LLMLingua team [11, 12] noted in passing that compressed prompts tend to produce shorter model outputs, but they did not isolate or quantify the effect. As far as I can find, this is the first controlled measurement of the phenomenon on a coding benchmark: **concise input causes concise output, and the output side is where the money is.**

## Compressed Error Feedback Is More Token-Efficient

One additional finding from the iterative framework: when the treatment arm retries, each retry adds fewer tokens to the context.

| Metric | Control | Treatment (Exp 1) | Treatment (Exp 2) |
|---|---|---|---|
| Avg tokens added per retry | +289 | +179 | +191 |
| Improvement rate (% of retries that fix the bug) | 38.5% | 45.5% | 45.5% |

In Experiment 1, the treatment's error feedback is 38% more token-efficient per retry, while achieving a *higher* fix rate (45.5% vs 38.5%). Concise prompting doesn't just produce shorter first-attempt outputs — it produces shorter error messages and shorter retry cycles, compounding the savings across iterative attempts.

Experiment 2 compounds this further by explicitly minifying the generated code before embedding it in error feedback. Each retry's context includes a minified version of the previous attempt's code (comments stripped, whitespace collapsed), rather than the raw LLM output. This directly reduces token growth on retries — a significant lever in iterative settings where error feedback accumulates.

## Limitations

- **Single model**: All experiments used Claude Sonnet. The output-conciseness effect may vary across model families. The 5x output pricing ratio holds for Anthropic's full lineup but varies across providers (3-5x is typical).
- **Single benchmark**: HumanEval is 164 self-contained function-generation problems. Real-world software engineering involves multi-file edits, test writing, debugging, and architectural decisions. Benchmarks like SWE-bench would provide stronger ecological validity.
- **Accuracy delta is negligible**: Prompt engineering shows identical solve rates (97.6% vs 97.6%), and minification is directionally *higher* (98.2% vs 97.6%, +0.6pp, not significant). Neither intervention degrades accuracy on HumanEval, but with harder problems, a conciseness instruction could plausibly degrade quality more. The cost-accuracy tradeoff needs characterization across difficulty levels.
- **Minification removes comments**: Experiment 2 strips comments from input prompts and generated code. On HumanEval, problem-relevant information lives in docstrings (which are preserved), so comment removal is safe. On real-world code with meaningful inline comments, this could remove useful context — a boundary worth testing.
- **Latency measured but not energy**: The framework now collects per-call API latency. Fewer output tokens should also reduce energy consumption, but energy has not been measured directly.

## What's Next

The iterative CPS framework generalizes beyond these two experiments. Directions I want to explore:

- **Cross-model comparison**: Run the same experiments on GPT-4o, Gemini, and open-weight models to determine if the output-conciseness effect is universal or model-specific
- **SWE-bench evaluation**: Apply the iterative framework to multi-file software engineering tasks where retry dynamics are richer and more representative
- **Compression stacking**: Combine prompt engineering + minification + algorithmic compression (e.g., LLMLingua-2 [12]) and measure whether savings are additive or diminishing
- **Energy measurement**: The framework already collects per-call API latency; adding energy consumption measurement (where possible) would enable a cost-latency-energy Pareto frontier

The iterative evaluation framework is open-source: [github.com/lneishloss/itereval](https://github.com/lneishloss/itereval). It supports pluggable input transformations, configurable retry budgets, and any Anthropic model. Contributions and reproductions are welcome.
